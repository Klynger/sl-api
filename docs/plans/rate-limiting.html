Plan: Rate Limiting and Brute-Force Protection

Closing security finding #7, and using it as a vehicle to implement the same protection at several abstraction layers, to understand what each layer is good at.

Status App layer done

The application-layer defense (phase 1) is implemented: per-IP rate limiting on the login route, returning a 429 in the standard error shape, verified in the smoke test. Every layer below it is intentionally scoped as a later learning exercise: re-solve the same problem at a different layer and compare. This is deliberate over-engineering for the sake of understanding infra and backend tradeoffs, not something a shopping-list app needs in production.

The core idea: two different problems

"Rate limiting" is really two problems that belong at different layers, and conflating them is what makes people reach for the wrong tool.

  • Generic volumetric limiting ("too many requests from this source"). Infrastructure's job. It does not need to understand the app; it counts requests per IP or route and sheds the excess.
  • Auth-specific brute-force protection ("too many failed logins for this account"). Only the application can do this, because only the app knows the semantic outcome: that a request was a login and that it failed. A gateway sees POST /v1/users/login -> 401; it does not know that is the 200th failed attempt on the account admin.

Finding #7 is fundamentally the second problem, but a complete defense uses both. They are complementary, not either/or.

Why this matters extra here. The bcrypt work from findings #1 and #6 spends about 60ms of CPU per login attempt by design. That cost is now a weapon: an attacker flooding the login endpoint can exhaust CPU cheaply. So we specifically want a cheap early reject in front of the expensive bcrypt path, which is exactly what a rate limiter provides.

On the service mesh instinct. A mesh can rate-limit at its ingress (it is Envoy underneath), but using a whole mesh to throttle a login endpoint is like installing a factory robot to open a jar. Its real job is east-west traffic, and it still cannot see that a login failed. It is included below as an experiment to feel that mismatch firsthand, not as a recommended fix.

Why no single layer is enough

  • Infra alone stops volumetric attacks but misses "low and slow" distributed brute force: a botnet doing one attempt per IP across thousands of IPs stays under any per-IP limit while hammering a single account. Only per-account tracking in the app catches that.
  • App alone means every abusive request still reaches the app and burns resources (see the bcrypt amplification above). Volume should be shed earlier.

Hence: infra for volume, app for identity-aware abuse. For finding #7 specifically, the piece that must live in our code is the application layer, which is why it goes first.

Phase 1: application layer (done)

Implemented and merged. Scope:

  • Per-IP rate limiting on the login route using github.com/go-chi/httprate as chi middleware, sitting in front of the bcrypt path.
  • A 429 response in the app's standard error shape ({"errors": [{code, detail}]}), via a new CodeRateLimited and a TooManyRequests helper in the errors package.
  • Counters kept in memory to start (see the storage note). Fine for a single instance.
Proxy caveat baked in from the start. Keying by IP uses the connection's remote address, which is correct when nothing sits in front. The moment a reverse proxy or load balancer is added (phase 4+), the remote address becomes the proxy, so keying must switch to a trusted X-Forwarded-For / X-Real-IP value. Trusting those headers blindly is itself a spoofing risk, so it must be paired with a trusted-proxy configuration. This is called out here so the later infra phases handle it deliberately.

Where the counters live

Any limiter needs to store counts somewhere. Same tradeoff as the sessions work (docs/plans/postgres-sessions.html):

  • In-memory (per process): trivial, zero infra, but resets on restart and does not coordinate across instances. Correct for a single-instance app, which is where we are.
  • Shared store (Redis or Postgres): needed once more than one instance runs, so they all see the same counts. Do not add it before running multiple instances.

Phases 1 to 3 are real hardening the app should keep. Phases 4 to 7 are the deliberate over-engineering: each one re-solves the same problem at a different layer purely to build intuition about the tradeoffs, and can be torn down afterward.

Open questions to decide per phase

  • Limits and window: what request-per-window is right for login? Start conservative (e.g. a few per minute per IP) and tune against the smoke test.
  • Lockout policy (phase 2): hard lockout after N failures, or exponential backoff? Backoff is friendlier to legitimate users who mistype; lockout is simpler. How is a lockout cleared (time, or an out-of-band reset)?
  • Response shape: should a 429 include a Retry-After header? Useful for clients, and cheap to add.
  • Which routes beyond login? Registration (account-creation spam) and, later, invite creation are candidates. Kept out of phase 1 to stay focused.
