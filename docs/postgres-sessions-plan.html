Plan: Postgres-Backed Sessions

Moving authentication from a stateless signed cookie to server-side sessions stored in Postgres, so the server owns identity and can revoke it. Design and phased implementation plan. Nothing here is built yet.

Why this exists. Today the cookie is the identity: it carries user_id and is only signed, so the server holds no session state and cannot revoke a session before it expires. This plan replaces that with an opaque session token backed by a database row, which enables logout-everywhere, killing a stolen session, and forcing logout on password change. As a bonus it removes the session signing secret entirely, closing several items from the security review.

Goals and non-goals

Goals

  • The server, not the cookie, is the source of truth for who is logged in.
  • Sessions can be revoked instantly (single session, all of a user's sessions, or on password change).
  • The cookie carries only an opaque, unguessable token with no identity or readable data inside it.
  • Cookie flags (HttpOnly, Secure, SameSite) are set correctly and unconditionally, not tied to debug mode.

Non-goals (for this iteration)

  • Redis or any new infrastructure. We already run Postgres; use it. Redis stays a later optimization if lookups ever become a measured bottleneck.
  • Refresh-token / short-lived-access-token hybrid. Overkill for now.
  • Fixing the committed secret storage strategy (tracked separately). This plan removes the need for a session secret, which helps, but the DB password handling is out of scope here.

How it works, end to end

  1. Login: after the password check, generate a random 32-byte token. Store a SHA-256 hash of it in a new sessions row along with the user id and an expiry. Send the raw token to the browser in a cookie.
  2. Each request: the middleware reads the token from the cookie, hashes it, looks up a non-expired sessions row by that hash, and loads user_id into the request context. No match or expired means 401.
  3. Logout: delete the session row and clear the cookie. The token is now dead everywhere immediately.
  4. Revocation: delete the relevant rows. All of a user's sessions, or a specific one.
Why store a hash of the token, not the token itself? The raw token lives only in the user's cookie. The database stores only its SHA-256, so a database leak does not hand an attacker a pile of live sessions (they would have the hashes, which are useless for logging in). Same reasoning as hashing passwords, applied to session tokens. A fast hash like SHA-256 is fine here because the token is already high-entropy random, so there is nothing to brute-force.
Do we still need to sign the cookie? No. The token is 256 bits of randomness that must exactly match a stored row, so it is unguessable on its own. That means we can drop gorilla/sessions and its signing secret entirely and set a plain http.Cookie. Fewer moving parts, and the session signing secret from the review simply ceases to exist.

Schema

A new migration, migrations/00002_create_sessions_table.sql (the baseline 00001_init_schema.sql is left untouched).

CREATE TABLE sessions (
  id           UUID PRIMARY KEY,
  token_hash   TEXT NOT NULL UNIQUE,          -- SHA-256 of the cookie token
  user_id      UUID NOT NULL,
  expires_at   TIMESTAMP NOT NULL,
  created_at   TIMESTAMP NOT NULL,
  last_used_at TIMESTAMP NOT NULL,
  user_agent   TEXT,                          -- optional, for "list my sessions"
  ip           TEXT,                          -- optional
  CONSTRAINT fk_user FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE
);

CREATE INDEX idx_sessions_user_id ON sessions (user_id);
CREATE INDEX idx_sessions_expires_at ON sessions (expires_at);
Deliberate divergence from the soft-delete convention. Every other table uses deleted_at for soft deletes. Sessions should be hard deleted: a revoked session must actually be gone, not merely flagged, or revocation is not real. So this table has no deleted_at, and logout / cleanup issue real DELETEs. Worth a one-line comment in the migration so the difference reads as intentional.

New capabilities this unlocks

  • Logout everywhere: DeleteByUserID, useful as its own endpoint or on password change.
  • List active sessions: ListByUserID, so a user can see their logged-in devices (this is why user_agent / ip are in the schema).
  • Kill a stolen session: delete a single row.

These are optional endpoints; the core plan does not require them, but the schema is built so they are trivial to add later.

Expiration and cleanup

Two layers, both needed:

  • Lazy: the lookup query filters expires_at > now(), so an expired session is never honored even if the row still exists.
  • Sweep: a background goroutine on a ticker (say every 15 minutes) runs DeleteExpired so dead rows do not accumulate. Simple, no new infrastructure. Could later become a scheduled job if preferred.

Sliding vs absolute expiry is a decision to make (see open questions). Sliding (extend on each request via Touch) matches the current behavior where the cookie is refreshed on every authenticated request.

What this fixes from the security review

#3 Cookie signed but not encryptedResolved. The cookie contains only a random token, no user_id or username, so there is nothing readable to expose.
#4 Cookie not HttpOnly / SecureFixed here. Flags are set correctly and unconditionally in the new cookie code.

Tradeoffs, honestly

  • A DB read per authenticated request. It is a single indexed lookup on token_hash, negligible at this scale, but the database is now on the auth hot path. Sliding expiry adds a small write per request; if that becomes noticeable, throttle the Touch (only extend when the session is past, say, half its life).
  • The store is a new dependency. If Postgres is down, auth is down. That was already effectively true for this app.
  • More moving parts than a stateless cookie. A table, a repository, a cleanup loop. The payoff is revocation and server-owned identity.

Phases 1 and 2 are self-contained and mergeable on their own. Phases 3 to 5 are one logical switchover and probably want to land together so the app is never half-migrated.

Open questions to decide before building

  • Sliding or absolute expiry? Sliding matches today's refresh-on-each-request behavior; absolute is simpler and more predictable. Leaning sliding, with throttled writes.
  • SameSite value? Lax is a good default for a same-origin app. Strict if there is never any cross-site navigation into an authenticated page; None only if a separate front-end origin needs it (and then Secure is mandatory).
  • One session per login, always? Yes to start. Concurrent logins each get their own row, which is the point of "list my sessions."
  • Store ip / user_agent now or later? Cheap to add columns now even if the listing endpoint comes later; migrations to add columns afterward are more friction.
